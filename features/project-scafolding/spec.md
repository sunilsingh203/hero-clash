# Spec: Project Scaffold & Data Model

## 1. Feature Summary and Goal

Establish the foundational Spring Boot/Maven project for Hero Clash: a compilable, runnable skeleton with the correct package layout, JPA entities for `Card`, `Player`, and `Room`, corresponding Spring Data repositories, a chosen schema-management strategy, and a local Postgres dev environment via Docker Compose. No game logic, REST endpoints, or WebSocket wiring is included — this feature exists purely so later features (card seeding, room REST API, WebSocket layer, game engine) have a stable base to build on.

Goal: `mvn clean install` builds successfully, the app starts cleanly against an empty Postgres database with zero errors, and at least one repository round-trip test (save + fetch) passes.

## 2. Functional Requirements

1. The project MUST build with Maven, targeting Java 21 and Spring Boot 3.x, via `mvn clean install`.
2. The project MUST include `spring-boot-starter-data-jpa` and the PostgreSQL JDBC driver as dependencies.
3. Database connection settings (URL, username, password, driver) MUST be externalized in `application.yml`, pointing at a local Postgres instance by default.
4. Source code MUST be organized under `com.herobattle` with packages `config/`, `controller/`, `model/`, `repository/`, `service/`, matching `CLAUDE.md`. Empty packages may contain a `.gitkeep` or be omitted until populated in later features (`controller/`, `service/`, `config/` may be empty in this feature).
5. A `Card` JPA entity MUST exist in `model/` with fields: `id` (Long, auto-generated), `name` (String), `alignment` (String), `imageUrl` (String), `intelligence`, `strength`, `speed`, `durability`, `power`, `combat` (all Integer, valid range 0–100, not enforced at the DB layer in this feature — see Edge Cases).
6. A `Room` JPA entity MUST exist in `model/` with fields: `id` (Long, auto-generated), `code` (String, unique, 6 characters), `status` (enum: `WAITING`, `IN_PROGRESS`, `FINISHED`).
7. A `Player` JPA entity MUST exist in `model/` with fields: `id` (Long, auto-generated), `displayName` (String), `sessionId` (String), and a many-to-one relationship to `Room` (FK `room_id`).
8. Each entity MUST have a corresponding Spring Data JPA repository interface in `repository/`: `CardRepository`, `PlayerRepository`, `RoomRepository`, each extending `JpaRepository<Entity, Long>`.
9. `RoomRepository` MUST declare a derived query method `Optional<Room> findByCode(String code)`.
10. Schema management strategy MUST be chosen (Flyway migrations vs. Hibernate `ddl-auto=update`) and documented in-repo (README or code comment) with a one-line tradeoff rationale. Decision for this feature: use Hibernate `ddl-auto=update` (see Data Model Changes section for rationale) — no Flyway migration files in this feature.
11. A `docker-compose.yml` MUST define a `postgres` service (official `postgres` image) exposing the standard Postgres port, with a named volume for data persistence, and environment variables for DB name/user/password matching `application.yml`.
12. Running `docker compose up -d` followed by `mvn spring-boot:run` MUST start the app with no startup errors against an empty database (schema auto-created).
13. At least one repository-layer test MUST exist (e.g., using `@DataJpaTest` or a Testcontainers/embedded setup) that saves and fetches a `Room` entity, asserting the round-trip succeeds.

## 3. API / WebSocket Message or Method Signature Changes

None. This feature introduces no REST controllers, `@MessageMapping` handlers, or WebSocket configuration. `controller/` and `config/` packages remain empty (or absent) in this feature.

Repository method signatures introduced (not REST/WebSocket, but the only "interface" surface this feature adds):

```java
public interface CardRepository extends JpaRepository<Card, Long> {}

public interface PlayerRepository extends JpaRepository<Player, Long> {}

public interface RoomRepository extends JpaRepository<Room, Long> {
    Optional<Room> findByCode(String code);
}
```

**`room`**
| Column | Type | Constraints |
|---|---|---|
| id | BIGINT | PK, auto-increment |
| code | VARCHAR(6) | NOT NULL, UNIQUE |
| status | VARCHAR | NOT NULL (enum stored as `@Enumerated(EnumType.STRING)`) |

**`player`**
| Column | Type | Constraints |
|---|---|---|
| id | BIGINT | PK, auto-increment |
| display_name | VARCHAR | NOT NULL |
| session_id | VARCHAR | |
| room_id | BIGINT | FK → `room.id`, nullable (player may exist before joining a room in later features) |

**Schema strategy decision:** Hibernate `ddl-auto=update` for this feature. Tradeoff: faster iteration while entities are still being shaped across early feature branches, at the cost of no versioned/reversible migration history and risk of drift in production-like environments. Flyway should be introduced no later than the feature that first deploys to a shared/persistent environment (tracked as follow-up, not blocking this feature).

No changes to Redis or RabbitMQ state — those are out of scope until later features per the build order.

## 5. Edge Cases and Error Handling

1. **Missing/unreachable Postgres on startup** — app fails fast with Spring Boot's standard connection-failure error; no custom retry/circuit-breaker logic is in scope for this feature.
2. **Duplicate `Room.code`** — the unique constraint at the DB level will throw a `DataIntegrityViolationException` on insert; no service-layer handling/retry is implemented in this feature (room-code generation/collision handling belongs to the Room REST feature).
3. **Powerstat values outside 0–100** — not validated in this feature (no Bean Validation annotations required); validation is deferred to the card-seeding feature, which controls all writes to `Card`.
4. **`Player.roomId` FK pointing to a deleted `Room`** — no cascade or orphan-removal behavior is defined in this feature since no delete operations exist yet; default JPA behavior (FK constraint blocks delete) applies.
5. **Empty package directories** (`controller/`, `service/`, `config/`) — acceptable to leave absent from source control until a later feature adds their first class; not a build failure.
6. **Running `mvn spring-boot:run` without `docker compose up -d` first** — expected to fail with a connection error; this is documented, not handled programmatically.

## 6. Out of Scope

- REST endpoints or controllers (`RoomController`, etc.)
- WebSocket/STOMP configuration
- Card data seeding from the akabab API
- Game logic / `GameEngine` / `GameSession` entity
- Authentication or session security
- Redis-backed room state
- RabbitMQ / STOMP broker relay
- Flyway migrations (deferred per schema-strategy decision above)
- Bean Validation constraints on entity fields
- CI pipeline (GitHub Actions) — introduced in a later feature per the build order
